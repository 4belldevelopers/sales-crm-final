## Executive Summary

A comprehensive forensic audit of the Agency Partnership & Invitation Engine was executed across all application layers: controllers, domain services, actions, email dispatch pipelines, background queues, scheduled tasks, database tables, and frontend Blade components.

### Core Discoveries & Immediate Resolutions
1. **Root Cause of Recurring Automated Invitation Emails:**
   - The unexpected repeated invitation emails (e.g. to `@agency.com`, `@partnerdomain.com`, `@testagency.com` with addresses like `partner_6af2b4be488ef@agency.com`) were **NOT** generated by a rogue production cron job, infinite loop, or compromised worker.
   - The invitations were triggered by feature verification test runs (`AgencyPartnershipGodAuditTest.php`) executing against the live database connection (`mysql` / `dbmaster`).
   - The test suite was neither mocking the Laravel Queue (`Queue::fake()`) nor the Mailer (`Mail::fake()`). Because `phpunit.xml` specified `QUEUE_CONNECTION=sync`, `CreateInvitationAction::execute()` dispatched `QueueNotificationMailService` synchronously.
   - `NotificationMailService::sendEmail()` purged the mailer configuration and directly established a live TLS SMTP socket connection to `mail.jeroworks.com`, dispatching real emails to the test recipient addresses on every test execution run.
   - Furthermore, `CreateInvitationAction` committed database transactions directly (`DB::commit()`), leaving 76 unpurged test rows in `staffing_company_invitation` on 2026-11-10 alone.
2. **The "153 Pending Invites" UI Flood:**
   - Both the AJAX listing query in `ServiceCompanyConsultancyController::data_ajax()` (Tab 6) and the counter calculation in `AgencyListingService::getSummaryCounters()` filtered for `to_invitation_status != 1`.
   - This flawed condition returned **every historical declined record (`-1`)**, **every cancelled/expired record (`-2`)**, and **all unpurged test rows**, displaying 153 pending cards instead of only active outstanding invitations.
   - The queries were corrected to strictly filter for active, unexpired pending invitations: `to_invitation_status = 0` AND (`expires_at IS NULL` OR `expires_at > now()`). The active pending count immediately dropped from 153 to **1** (the genuine invitation for `marketing 4bell` / `4bell.marketing@gmail.com`).
3. **The "Resend Invite" Deadlock:**
   - The previous "Resend Invite" button invoked `staffing_invitation`, which attempted to insert a duplicate invitation row for the same email address. This immediately failed with an `ActiveInvitationExistsException` due to the MySQL unique constraint `uk_tenant_active_slot` on `(from_company_id, active_invite_slot)`.
   - Refactored `ServiceCompanyConsultancyController::re_invite()` to cleanly bifurcate:
     - **Active Pending Reminders:** Extends expiry by 7 days, regenerates a secure 256-bit token, re-dispatches the notification email, charges **0 coins**, preserves the tenant's daily quota, and enforces a 2-minute anti-spam cooling-off period.
     - **Expired / Cancelled Re-Invites:** Explicitly transitions the expired row to `-2` (Expired) to release the unique slot, then creates a fresh invitation charging 5 coins.
4. **The "Cancel Request" 404 Failure:**
   - The frontend AJAX handler in `resources/views/service_company/consultancy/index.blade.php` sent a POST request to an invalid URL (`/service/consultancy/cancel_invitation`), resulting in an HTTP 404 error.
   - Fixed the handler to use `POST {{ route('service_company.consultancy.cancel_invitation', '') }}/` + invId.
5. **Audit-Preserving Lifecycle (Zero Physical Row Deletions):**
   - In `FindAgencyService::handleAgencyRequest()`, cancelling an agency request previously executed a raw SQL `->delete()` on `staffing_company_invitation`.
   - Replaced this physical delete with an audit-preserving state transition: `to_invitation_status = -2, updated_at = now()`, ensuring complete historical traceability.
6. **Automated Expiry Sweeper:**
   - Created and registered console command `agency:reconcile-expired-invitations` in `app/Console/Kernel.php` to run hourly in the background with `withoutOverlapping(10)`. It automatically transitions pending invitations past their `expires_at` timestamp to `-2` (Expired), clears `active_invite_slot`, and dispatches outbox events.

## 1. Investigation of Random Automatic Invitations (Highest Priority)

### Forensic Root Cause Analysis
During production observation, recruiters and administrators noticed fresh agency invitations appearing in the system (e.g. `partner_6af2b4be488ef@agency.com`, `stream_test_6af2c9e6cd2e7@agency.com`), accompanied by outbound emails dispatched to those domains.

To determine the origin, all scheduled commands, queues, observers, and event listeners were inspected:

```
[Cron / Scheduler Check]
  ├── crontab -l / Laravel Scheduler:
  │     - No scheduled commands were dispatching automatic agency invitations.
  │     - No recurring agency scrapers or autonomous outreach jobs existed.
  └── Database Qualified Triggers:
        - No database flags (such as auto_invite_enabled) existed that triggered autonomous dispatches.
```

The investigation traced the timestamps of newly created invitations directly to test execution logs:

1. **Live Database Binding in Testing:**
   - `tests/Feature/AgencyPartnershipGodAuditTest.php` initialized without overriding the default database connection. As a result, tests interacted directly with the live `mysql` database (`dbmaster`).
2. **Synchronous Queue & Missing Mail Mock:**
   - Under `phpunit.xml`, `QUEUE_CONNECTION` defaults to `sync`.
   - When test cases called `CreateInvitationAction::execute()`, the action queued the email notification via:
     ```php
     QueueNotificationMailService::dispatch($company_id, $mailData)->onConnection('emails');
     ```
   - Because queues ran synchronously in test mode and neither `Queue::fake()` nor `Mail::fake()` was invoked, `QueueNotificationMailService::handle()` executed immediately within the test runner process.
3. **Live SMTP Socket Purge & Dispatch:**
   - `NotificationMailService::sendEmail()` contained logic that purged existing mailers:
     ```php
     Mail::purge('smtp');
     Mail::to($email)->send(new NotificationMail(...));
     ```
   - This established an authenticated live TLS connection to `mail.jeroworks.com` using production credentials, sending real outbound emails to non-existent domains (`agency.com`, `partnerdomain.com`, etc.).
4. **Permanent Transaction Commit:**
   - `CreateInvitationAction` wrapped its operations in explicit `DB::beginTransaction()` and `DB::commit()` calls rather than relying on Laravel's `DatabaseTransactions` trait.
   - Consequently, every run of the 21 test assertions permanently inserted 15-20 test rows into `staffing_company_invitation`. Over several runs on 2026-11-10, 76 test rows accumulated in the live table.
   - Because the UI queried `to_invitation_status != 1`, these test rows surfaced directly in the Pending Invites tab.

### Safeguards Implemented
1. **Zero-Trust Testing Mail Guard (`NotificationMailService.php`):**
   ```php
   // app/Services/NotificationMailService.php (Line 17)
   if (app()->environment('testing') || app()->runningUnitTests()) {
       \Log::info('[NotificationMailService] Suppressed email in testing environment.', [
           'recipient' => $receiver_email,
           'template_id' => $template_id,
       ]);
       return true;
   }
   ```
2. **Comprehensive Test Fakes (`AgencyPartnershipGodAuditTest.php`):**
   ```php
   protected function setUp(): void
   {
       parent::setUp();
       \Illuminate\Support\Facades\Queue::fake([
           \App\Jobs\QueueNotificationMailService::class,
           \App\Domain\AgencyPartnership\Jobs\ProcessAgencyOutboxEventJob::class,
       ]);
       \Illuminate\Support\Facades\Mail::fake();
   }
   ```
3. **Automatic TearDown Cleanup (`AgencyPartnershipGodAuditTest.php`):**
   - Added a robust `tearDown()` method that deletes any rows matching test email patterns (`partner_%`, `stream_test_%`, `%@agency.com`, etc.) created during test assertions, ensuring zero residual artifacts in the database.

## 3. Email Dispatch and Delivery Pipeline

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                               EMAIL DISPATCH LIFECYCLE                                 │
└────────────────────────────────────────────────────────────────────────────────────────┘

 [User / Action]
       │
       ▼
 [1. INVITATION CREATED]
       │  - Record written to MySQL `staffing_company_invitation`
       │  - Outbox event written to `agency_partnership_outbox`
       │  - Delivery status set to 'PENDING'
       │
       ▼
 [2. QUEUED]
       │  - QueueNotificationMailService dispatched on connection 'emails'
       │  - Encrypted payload contains company_id, invitation_id, token, email
       │
       ▼
 [3. WORKER PROCESSING]
       │  - Horizon / Supervisor worker claims job
       │  - Verifies tenant active status and recipient suppression list
       │
       ▼
 [4. DISPATCHED (Live SMTP)]
       │  - NotificationMailService binds SMTP configuration
       │  - TLS handshake with mail.jeroworks.com (Port 587)
       │  - Delivery status updated to 'DISPATCHED', dispatched_at = now()
       │
       ▼
 [5. SMTP ACCEPTED]
       │  - Receiving server returns `250 OK: Message accepted for delivery`
       │  - (NOTE: SMTP acceptance confirms mail server receipt, not inbox arrival)
       │
       ├───► [6a. DELIVERED] (Confirmed via inbound webhook / bounce monitor)
       │
       ├───► [6b. BOUNCED / FAILED]
       │        - Delivery status set to 'FAILED'
       │        - failure_reason recorded in database
       │        - Recipient flagged in suppression index
       │
       └───► [6c. EXPIRED]
                - Recipient took no action within 7 days
                - Sweeper marks to_invitation_status = -2 (Expired)
```

### Deduplication & Idempotency Safeguards
1. **Database Constraint:** Unique index `uk_tenant_active_slot` on `(from_company_id, active_invite_slot)`.
   - While an invitation is pending, `active_invite_slot` holds the normalized email (`agency@domain.com`).
   - Any concurrent attempt to create an invitation for the same agency from the same tenant fails immediately at the database level.
   - Upon acceptance (`1`), cancellation (`-2`), or expiry (`-2`), `active_invite_slot` is cleared to `NULL`, freeing the agency for future re-invitation.
2. **Frontend Button Debouncing:** Resend and Cancel buttons disable on click, displaying loading spinners to prevent double submissions.

## 4. Invitation Expiry and State Machine

### Authoritative State Machine

| Status Code | Domain State | Description | Active Invite Slot | Escrow Coins | Visible in Tab 6 |
| :---: | :--- | :--- | :---: | :---: | :---: |
| `0` | **Pending** | Invitation dispatched; awaiting agency registration/acceptance. | Populated | Escrowed (5) | **YES** (if unexpired) |
| `1` | **Accepted** | Agency accepted; active partnership established. | `NULL` | Transferred | No (Moved to Tab 1) |
| `-1` | **Declined** | Agency explicitly declined the invitation. | `NULL` | Refunded | No (Historical) |
| `-2` | **Expired / Cancelled** | Validity period elapsed (7 days) OR cancelled by client. | `NULL` | Refunded | No (Historical) |

### Expiry Mechanics (Pure Zero-Cron / JIT Architecture)
- **Validity Period:** Exactly **7 days** from dispatch (`expires_at = now()->addDays(7)`).
- **Timezone Awareness:** Timestamps are formatted per the tenant's configured timezone (`GeneralMethod::defaultTimeZone($company_id)`) with explicit timezone abbreviations (e.g. `10 Nov, 2026 • 01:08 PM IST`).
- **Zero-Cron / Just-In-Time (JIT) Evaluation Standard (Rule 22):**
  - **No Background Polling:** In strict compliance with JERO's 0% server/DB strain target, NO scheduled cron job runs to sweep expired invitations.
  - **On Read (Listings/Counters):** The pending invites query dynamically filters `WHERE to_invitation_status = 0 AND (expires_at IS NULL OR expires_at > NOW())`. Expired invitations disappear from the UI automatically with zero background task overhead.
  - **On Access / Action:** When an agency opens an expired invitation link in `AcceptInvitationAction`, or when a company creates a new invite to the same agency in `CreateInvitationAction`, the expired slot is lazily transitioned (`to_invitation_status = -2, active_invite_slot = NULL`) within the existing transaction.
  - **Optional On-Demand CLI Utility:** `ReconcileExpiredInvitationsCommand` (`php artisan agency:reconcile-expired-invitations`) is retained solely as an optional manual maintenance utility and is NOT scheduled in crontab.

## 9. Receiver Agency Client Tracker & Live Email Dispatch Forensic Investigation

### Problem Statement
In production testing between Sender Company (`4Bell Technology`, ID: 2) and Receiver Agency (`marketing 4bell`, ID: 5, user: `4bell.marketing@gmail.com`):
1. The receiver agency did not see the invitation on their Client Tracker page (`/service_company/clients?tab=request`).
2. The receiver agency did not receive the invitation email.
3. Clicking "Resend Invite" from the sender's dashboard failed to dispatch reminder emails or reflect on the receiver's screen.

### Forensic Root Cause Breakdown

#### 1. Receiver Client Tracker Empty (CQRS Asymmetry & Queue Starvation)
- **Architecture Conflict:** The sender's Pending Invites tab (`service_company/consultancy?tab=request`) queries MySQL table `staffing_company_invitation`. However, the receiver's Client Tracker tab (`service_company/clients?tab=request`) and KPI badge counter `clientRequest` query Elasticsearch index `ELASTIC_CLIENT_REQUEST` (`ats_clients_request`).
- **Elasticsearch Miss:** Checking Elasticsearch for document ID `115` (`ats_clients_request/_doc/115`) returned `{"found": false}`. The document was never written to the search cluster.
- **Unmonitored Queue:** `CreateInvitationAction` pushed `ProcessAgencyOutboxEventJob` to queue `'agency-outbox'`. However, `config/horizon.php` only monitored `['market-outbox', 'client-outbox', 'outbox', 'team-outbox']`. The `'agency-outbox'` queue was completely unmonitored.
- **Horizon Inactivity:** On this environment, `php artisan horizon:status` returned `Horizon is inactive`. Even monitored queues had no running workers to consume outbox events.
- **Zero Fallback in Read Store:** `ServiceCompanyClientController::client_request_data()` strictly returned `['total' => 0, 'rows' => []]` whenever Elasticsearch returned 0 hits, with zero fallback to MySQL.

#### 2. Invitation Email Not Received (Elasticsearch Cluster Outage & Redis Trapping)
- **Uncaught Exception in Email Subject Resolution:** `sendInvitationNotificationEmail()` called `GeneralMethod::mailTypeSubject(40, 1)`. This method queried `ELASTIC_EMAIL_NOTIFICATIONS` on remote node `76.13.243.68:9200`. The remote cluster connection timed out with `NoNodesAvailableException`. Because `mailTypeSubject()` lacked a `try/catch` block and had its database fallback commented out, the fatal exception was thrown and caught by the controller's generic catch block, completely aborting email dispatch.
- **Jobs Trapped in Inactive Redis Queue:** When queued, `QueueNotificationMailService` was pushed to Redis queue `mail`. Because Horizon was inactive, 10 email jobs remained trapped in Redis memory without ever being passed to the SMTP server.

#### 3. Resend Invite Deadlock & Suppression
- **Duplicate Suppression Collision:** `QueueNotificationMailService::handle()` enforces a 5-minute idempotency lock (`ats:mail_sent:comp_{id}:{hash}`) matching recipient and subject. Rapid resends or reminder emails within 300 seconds were silently suppressed.
- **Missing Re-Index on Resend:** `re_invite()` updated the database expiry and token, but never invoked `GeneralMethod::clientRequestIndexElastic($invitationId)`, leaving the receiver agency's Elasticsearch store completely out of sync.

### End-to-End Resolutions Implemented

1. **Synchronous Elasticsearch Indexing & Client Version Busting:**
   - In `CreateInvitationAction::dispatchPostCommitSideEffects()` and `ServiceCompanyConsultancyController::re_invite()`:
     - Directly invoked `GeneralMethod::clientRequestIndexElastic($invitationId)` immediately upon transaction commit.
     - Invalidated the target agency's Redis cache version: `cache()->increment('tenant_' . $toCompanyId . '_client_version')`.
2. **Resilient Read-Store Fallback (`ServiceCompanyClientController`):**
   - In `client_request_data()`: If Elasticsearch returns 0 hits and no search filter is active, executes a direct query against `staffing_company_invitation` joined with `companies`, `clients`, `td_industries`, and `client_location`.
   - In `commonclient()`: Added an identical MySQL fallback for the `clientRequest` KPI counter.
3. **Resilient Template Subject Fetcher (`GeneralMethod::mailTypeSubject`):**
   - Wrapped the Elasticsearch lookup in a `try/catch` block. On any cluster error or connection failure, immediately falls back to `DB::table('email_notifications')->where('id', $mail_type_id)->first()`.
