# 96 — Invariants (kept-true across the resume upload subsystem)

> *Intent: lock down the few rules that MUST hold across the system. These are*
> *non-negotiable design rules. If a PR breaks one of them, the PR is closed*
> *on review, regardless of how good the rest of it looks.*

## Reading order

1. INV-1 — session UUID lifecycle
2. INV-2 — manual values always win
3. INV-3 — submit idempotency via server state
4. INV-4 — overall upload idempotency
5. INV-5 — parser result belongs to one session

Each invariant below shows: **canonical statement**, **where it lives**,
**what enforces it**, **the test that proves it holds**.

## INV-1 — Every user-initiated file pick creates a brand-new session

**Canonical:** Every user-initiated file selection creates exactly one
new `upload_session_uuid` and exactly one new `resume_uploads` row. The
upload subsystem performs **no business duplicate detection**. Two
different file picks always produce two different sessions, even if the
same file bytes are picked twice in a row. Candidate duplicate detection
happens only at submit time, in the **Duplicate Ownership Engine**
(separate system; outside the upload subsystem — see Step 20 for the
explicit "duplicates are created and kept; engine only DETECTS and
REPORTS, never MERGES" contract).

**Where it lives:**
- DB: `resume_uploads.idempotency_key` column for HTTP-retry replay
  (NOT for content dedupe). NO UNIQUE constraint — replay is
  "last-N-lookup", not a uniqueness gate.
- Server: `ResumeUploadSession::createOrPresign()` reads the
  `Idempotency-Key` request header, looks up the most recent
  non-terminal session with the same key for the same `company_id`,
  returns it if found.
- Browser: `Idempotency-Key` value is a **per-request random** token
  generated by JS (`crypto.randomUUID()`) at the moment of presign
  request construction. Kept in the JS module closure (NOT
  `localStorage` — which would survive past session expiry and cause
  stale replays). Discarded after the response is processed.
- New file pick → new closure, new key, new session. Always.

- `test_http_retry_same_header_returns_same_uuid`
- `test_new_request_header_creates_new_uuid_even_within_same_session`
- `test_new_file_pick_with_new_header_creates_new_uuid`
- `test_two_file_picks_with_same_bytes_produce_two_sessions` (Step 20)
- `test_upload_succeeds_even_when_existing_resume_with_same_sha256_exists` (Step 20)

## INV-2 — Parser may populate empty fields only

**Canonical:** Parser prefill never overwrites a non-empty input. The
recruiter's typed value wins; the parser's value goes into the input
only if the input was empty **and** the parser's value is non-empty.

**Where it lives:**
- Blade: `<input … data-parser-populated="false">` attribute.
- JS: `resume-populate-if-empty.js` checks
  `!input.value && input.dataset.parserPopulated === 'false'`
  before assigning.
- Server: `ResumeParserService` does not write back into the form; the
  JS read is independent. Server writes only to
  `resume_parse_results.payload`.

**Test:** `tests/Feature/ResumeV2Invariant2Test.php`
- `test_manual_values_always_win_over_parser` (the test name is fixed;
  see ADR-013)
- `test_parser_payload_writes_to_parse_results_table_not_applicant_fields`

## INV-3 — Submission may retry, but server verifies state before any insert

**Canonical:** The browser MAY auto-retry a `POST /candidates` that
failed at the network layer. The server MUST verify the session state
on every attempt BEFORE inserting. If `linked_candidate_id` is already
set, server returns the existing candidate (HTTP 200) instead of
inserting a duplicate.

This invariant also covers the **cross-request race**: two pods
receiving the same valid `session_uuid` from the same recruiter
(double-click, multi-tab, network blip) MUST produce exactly one
candidate. The mechanism is the conditional UPDATE inside a
transaction: the first pod's `UPDATE … WHERE status='Uploaded'` claims
the session; the second pod's UPDATE finds zero rows and falls through
to the 200-winner-found path.

**Where it lives:**
- Controller: `ServiceCompanyJobApplicationController::store` (and
  the v2.5 unified variant) reads session first.
- DB: `resume_uploads.linked_candidate_id` UNIQUE behavior at
  application level (FK + DB constraint via `unique(company_id, session_uuid, linked_candidate_id)`).
- API: `EP-candidate-store` returns 200 with `note=session_replay_winner_found`
  on the INV-3 retry path. Never returns 200 on a Step 20 dup path —
  Step 20 dups always return 201 with the new candidate row.
- NOTE — disambiguation from Step 20: this INV-3 path is "same
  session, two concurrent submits, second reads back the first's
  candidate row". Step 20 is "different sessions, two candidates
  that both persist, the engine never merges them". These are
  DIFFERENT concepts; both have a "200 with existing candidate"
  surface but only INV-3 has it.
- DB: `UNIQUE(uuid, company_id)` on `resume_uploads` makes
  cross-tenant `session_uuid` probing structurally zero-leak —
  Tenant A submitting Tenant B's UUID is a guaranteed 422 because
  the lookup `WHERE uuid=? AND company_id=A` returns zero rows.

## INV-4 — HTTP retry safety only — NOT business dedupe

**Canonical:** The `Idempotency-Key` HTTP header is a **per-request
random token**, NOT a content hash. Same header on a retried POST →
server returns the previously-issued session. Different header on a new
POST → new session, regardless of file contents. **Two recruiters
picking the same file bytes → two different `Idempotency-Key` headers
(generated independently by their browsers) → two new sessions**;
both submit, both candidates exist forever; the Duplicate Ownership
Engine flags the dup to the recruiter (badge) but never merges
(Step 20).

This is transport-level retry safety (protects against network blips,
double-clicks, double-tab races). It is **not** "duplicate detection."
The canonical statement of "what is a duplicate resume at the candidate
level" is owned by the Duplicate Ownership Engine and is out of scope
for the upload subsystem.

**Where it lives:**
- Server: reads `Idempotency-Key` request header; persists the value on
  `resume_uploads.idempotency_key` for lookup.
- DB: `INDEX (company_id, idempotency_key)` exists for replay-lookup
  performance, NOT as a uniqueness gate. **No `UNIQUE` constraint.**
- Service: `ResumeUploadSession::createOrPresign()` checks
  `WHERE company_id = ? AND idempotency_key = ? AND status NOT IN
  (terminal)` and returns the most recent match if any. Otherwise
  INSERT a new row.

**Test:** `tests/Feature/ResumeV2Invariant4Test.php`
- `test_retry_with_same_header_returns_same_uuid`
- `test_new_header_creates_new_uuid_even_after_previous_session_linked`
- `test_replay_does_not_resurrect_terminal_session`

## INV-5 — One parser result belongs to one upload session

**Canonical:** There is at most one `resume_parse_results` row per
`resume_upload_id`. Parser dispatch is bounded: Laravel's
`ShouldBeUnique(60s)` AND `parser_attempts` is incremented BEFORE the
parse and capped at 1 server-side.

**Where it lives:**
- DB: `resume_parse_results.resume_upload_id` FK with `UNIQUE` per row.
- Job: `ParseResumeJob::uniqueId()` returns the `resumeUploadId`;
  `uniqueFor = 60`.
- Server: `ParseResumeJob::handle()` reads `parser_attempts` first
  and short-circuits if already attempted.

**Test:** `tests/Feature/ResumeV2Invariant5Test.php`
- `test_parser_dispatched_twice_within_60s_runs_only_once`
- `test_parser_attempts_incremented_before_parse_call`
- `test_parser_second_attempt_within_window_short_circuits`

## Frequently-asked review questions

**Q: "What if the recruiter really did want to re-upload the same file?"**
A: They get a brand-new UUID every time (INV-1). The file is uploaded
again, parsed again, and at submit time the Duplicate Ownership Engine
will tell them whether the new candidate is a duplicate of an existing
one. The upload subsystem's job is bytes-in-R2; dedupe is downstream.

**Q: "What if two recruiters in the same tenant upload the exact same
file independently?"**
A: Both uploads succeed. Each gets its own session, its own R2 object,
and (if both reach submit) its own `documents` row and **its own
candidate row that exists forever**. The Duplicate Ownership Engine
detects the cross-recruiter duplicate and shows a "possible duplicate"
badge on both candidates. The engine NEVER merges them. The recruiter
decides what to do (typically: manually archive one). See Step 20
for the full acceptance scenarios.

**Q: "What if two recruiters in DIFFERENT tenants upload the same file?"**
A: Two sessions in two different `company_id` namespaces. Two R2
objects. Two candidates, one per tenant, each existing forever.
The Duplicate Ownership Engine MUST NOT cross tenants by default
(CLAUDE.md rule 3, INV-3). Each tenant sees its own candidates and
its own duplicate-badges. Cross-tenant merging is forbidden; the
engine cannot mutate candidates across tenants. Step 20 acceptance
scenario 3.

**Q: "What if the browser retries the presign POST after a network blip?"**
A: INV-4 — same `Idempotency-Key` header → server returns the same
session. The JS module keeps the key in the closure scope and retries
the SAME fetch with the SAME key, so the server replays the previous
response (INV-4).

**Q: "What if the parser takes >30 s?"**
A: Status flips to `Failed` with `last_error='PAR_TIMEOUT'`. A retry
attempt by the recruiter re-runs the upload flow but the parser
itself never re-runs automatically — it's bounded to one attempt.

**Q: "What if the same browser opens two tabs at the same time?"**
A: BroadcastChannel keeps them in sync (v2.5, ADR-018). If they
both POST `/api/resume-sessions` with different `Idempotency-Key`
headers concurrently, INV-1 says two new UUIDs are issued — one per
tab. The user picks which tab's session to submit with; each submit is
its own transaction. Same-key concurrent POSTs → one UUID wins (INV-4).
